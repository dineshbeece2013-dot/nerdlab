You already know this pain

The problem

You and a partner, Jordan, are writing a group report. It goes like this: you email report.docx. Jordan edits it and emails back report_v2.docx. You add more and save report_v2_FINAL.docx. Jordan makes one more fix: report_v2_FINAL_ACTUALLY_FINAL.docx. Now nobody is sure which file has everyone's latest edits, and someone's paragraph just got overwritten by accident.

What Git actually is

Git is automatic, precise version history for a folder — like the "Version History" feature in Google Docs, except it works on any file, tracks exactly what changed and why, and never overwrites anything by accident. Instead of renaming files, you keep one file, and Git remembers every version of it forever.

The three places your work lives

📝 Working Filethe doc open on your screen right now
→
✅ Staging Areathe edits you've chosen to include in the next saved version
→
📚 Historyevery version ever saved, labeled and permanent

git add is you saying "these specific edits are ready to be part of the next version." git commit is you actually saving that version with a label, permanently, so you can always come back to it. No more file-name chaos — just one file and a real history behind it.

git init — turn on version history for this folder

Scenario

You made a folder called project-report and started an outline in report.txt. Right now, this is just a regular folder — if you overwrite something by mistake, it's gone. There's no history yet, because you haven't told Git to start keeping one.

What actually happens

git init creates a hidden .git folder inside project-report. That's where every future saved version will live. This is the one-time switch that turns on version history for this specific folder — like clicking "Enable Version History" for the first time. Nothing is saved yet; it just gets things ready.

git add — choose what counts as "done"

  

    
Scenario

    
You just finished writing the Introduction in report.txt. You also have a messy list of half-formed ideas typed at the bottom of the same file — not ready to be part of an official version yet. Before saving a real version, you need to tell Git exactly what should be included.

  

  

    
What actually happens

    
git add report.txt moves your edits into the staging area — a holding spot for "changes ready to be part of the next version." This step exists precisely so you're never forced to save everything blindly; you decide what's ready. git add . stages every changed file at once, when everything really is ready.

git commit — save a labeled version, permanently

  

    
Scenario

    
Your Introduction is staged. Now make it official: save this exact version with a short label describing what it is, so you (and Jordan) can always find it again.

  

  

    
What actually happens

    
git commit -m "message" takes everything staged and saves it as a permanent version in the history — like naming a save point in Google Docs' version history instead of relying on a vague auto-save timestamp. The message says what changed and why. This version can never be silently overwritten; it's there forever, ready to return to.

Branches — try a risky rewrite without touching the version everyone trusts

  

    
Scenario

    
Jordan wants to try restructuring the whole report around a different argument. It might be great — or it might be a dead end. Either way, you don't want to risk the version your team is currently relying on for tomorrow's deadline.

  

  

    
Why not just copy the file?

    
You could duplicate report.txt into report_alt.txt — but then you're back to the file-name chaos from the start, and there's no clean way to pull just the good parts back in later.

  

  

    
What actually happens

    
A branch is a separate, parallel version of the same file's history. git checkout -b restructure creates a branch called restructure and switches to it. Jordan can now rewrite freely — the trusted main version is completely untouched. If the rewrite works, its changes can be merged back into main; if not, the branch is simply abandoned and nothing is lost.

  


  
🎯 Your turn

  

    
Create and switch to a branch called restructure to try the risky rewrite safely:

    

      project-report (main) $
      
      
    

    

    

    
Hint: git checkout -b restructure — the -b means "create it, then switch to it."

  







  
Merging — combining two branches back together

  

    
Scenario

    
Jordan's rewrite on restructure turned out great. Meanwhile you kept working on main and, without realizing it, edited the exact same paragraph. Time to bring restructure back into main.

  

  

    
What actually happens

    
git merge restructure (run while on main) combines the two histories. If you and Jordan touched different parts of the file, Git merges them automatically — no conflict, no fuss. But since you both edited the exact same lines, Git can't guess which version you want. That's a merge conflict. Git pauses and marks the disputed spot right inside the file:

  

  

    
<<<<<<< HEAD
Your version of the paragraph...
=======
Jordan's version of the paragraph...
>>>>>>> restructure

  

  

    
How you resolve it

    
Open the file and edit it by hand: delete the <<<<<<</=======/>>>>>>> markers and keep whichever wording (or a blend of both) you actually want. Then it's the normal rhythm again — git add marks it resolved, and git commit finishes the merge (Git already fills in a sensible default message for you).

  


  
🎯 Your turn: work through a real conflict

  

    

      project-report (main) $
      
      
    

    

    

    
Hint: git merge restructure

Rebasing — a cleaner alternative to merging

  

    
Scenario

    
Before merging, Jordan wants the restructure branch's history to look like it was written straight on top of the latest main — one clean line instead of a fork-and-rejoin with a merge commit.

  

  

    
Merge vs. rebase

    
Merge keeps both histories exactly as they happened and adds one extra "joining" commit — honest, but the timeline visibly branches and rejoins. Rebase takes your branch's commits and replays them one by one on top of the latest main, as if you'd written them there all along — the result is a single straight line, easier to read later.

  

  

    
The one rule

    
Rebasing rewrites commit history (new commit IDs). That's fine for a branch only you're working on — but never rebase a branch other people have already pulled and built on top of; use merge for anything shared.

  


  
🎯 Your turn

  

    
While on restructure, replay its commits cleanly on top of the latest main:

    

      project-report (restructure) $
      
      
    

    

    

    
Hint: git rebase main

The takeaway

    
Every one of those "FINAL_v2_ACTUALLY_FINAL" moments from the intro is solved by exactly one of these commands. That's the whole point of Git: the rhythm of edit → stage → save a labeled version, with a real history behind it instead of a pile of filenames.

Cheat sheet

  

    
CommandWhat it doesReal-life equivalent

    
git initStarts tracking history in this folder (run once)Turning on "Version History" for the first time

    
git add <file>Stages a file for the next snapshotMarking these edits "ready" to be part of the next save

    
git add .Stages every changed fileMarking everything you changed as ready

    
git commit -m "msg"Permanently saves the staged snapshotNaming and saving a version, for good

    
git statusShows what's changed / staged / untracked"What's changed since I last saved?"

    
git logShows history of all commitsOpening the Version History panel

    
git checkout -b <name>Creates and switches to a new branchA safe copy that can still be merged back later

    
git branchLists existing branchesListing every in-progress alternate version

    
git merge <branch>Combines another branch's history into your current oneBringing an alternate version back into the main one

    
git rebase <branch>Replays your commits on top of another branch's latest workRewriting your notes to read as one clean line, not a fork-and-rejoin

  

  

    
Remember

    
The core loop is always: edit a file → git add → git commit. Status, log, and branches just help you see and safely navigate that history — no renamed files required.
